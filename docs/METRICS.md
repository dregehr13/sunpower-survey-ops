# Metric register

Every number the app displays, where it is defined, and which surfaces read it.
The point of this document is to make **drift visible**: when the same concept is
computed in two places, it eventually disagrees. That has happened three times
(three SS ratios differing 34% on one week; a completion test that ignored List
status for five months; a colour band that disagreed with the number beside it).

**All definitions live in `lib/metrics.cjs`.** Surfaces destructure from
`OpsMetrics` and must not redefine them — `test/surfaces.test.js` enforces this.

## Surfaces

| surface | file | what it renders |
|---|---|---|
| Dashboard | `index.html` | Current / WIP / Performance / Trends / Quality / Map / Resource / Billing / Data / Settings |
| Compose | `compose/index.html` | Monday recap + daily email |
| Morning card | `api/morning-card.js` | Teams card (not adopted — see CLAUDE.md) |

## The metrics

### Scope & classification

| metric | definition | trap |
|---|---|---|
| `DATA_CUTOFF` | `2025-12-29`; all charts and row filters start here | — |
| `effectiveComplete(r)` | `agreement_signed` when the survey completed **before** it, else `complete` | Cycle time measures against this, not the raw date. A cancelled account re-signed months later keeps its original survey; the row carries a real completion 175–231 days before the new agreement, which is correct data and must not be "fixed" in SF. The survey was in hand when the job entered the queue, so the cycle is zero. Fires on 5 rows; a no-op for the 42 same-day rep surveys, whose `complete` equals `agreement_signed` rather than preceding it |
| `agreement_signed` | the customer's signature date, 100% populated | **Not the cycle-time anchor** — `ct_total` stays on `start`, which is when the job reaches the SS queue. Same day as `start` on 87% of rows and never later. Explains the 42 rows completing a day before start: the rep signed and surveyed the same day, and the project record starts the next morning. Meaningless for resurveys |
| `opened` | the TaskRay task's creation date, 100% populated | **The default cycle-time anchor** since 2026-08-25. `applyAnchor()` in index.html folds it into `r.start` at load, so nothing downstream — including every function in this file — knows it exists. Ships as a datetime; typed `date` so `cleanDate()` strips the time. `filterable:false`: a filter on it would cut by one anchor while measuring by the other |
| `ct_open` | `opened` → `effectiveComplete(r)`, clamped at 0 | Baked beside `ct_total` at parse time so the Settings toggle is a swap, not a recomputation. No `field_survey_complete` fallback twin — that branch reconstructs a missing *completion*, which is orthogonal to the anchor. Read only by `applyAnchor()`; never by a surface |
| anchor overrides (`overrides.json`) | per-row hard-swap of `start` **and** `opened` to a manual date, keyed by task_id | For a project cancelled before survey and reactivated later on the same task, where SF's start counts a dead gap (2175DUND: 68d → 0d). Applied by `parse-sf.js` at import (baked into data.js, so compose and the morning card inherit it) and re-applied by `applyOverrides()` in index.html for a row overridden since the last push. `applyOverrides` runs before `applyAnchor` and sets `r._override` so `applyAnchor` skips the row; these two are the **only** writers of `r.start` (`test/surfaces.test.js`). Managed on the Data page → `api/update-overrides.js` (keeps the update password). The row stays counted everywhere — only its cycle time moves. `parse-sf.js` flags reactivated-after-cancel candidates (>21d, was Canceled last export) and stale/mislabelled override entries |
| `inScope(r)` | started ≥ cutoff **and** (complete **or** project active) | a finished survey counts even on an At-Risk/Canceled project; a *non-finished* one on such a project does not. Reads the anchored `r.start`, so the cutoff applies to the same date every metric measures from. Population is identical either way (2,444 rows) |
| `filterRows(raw)` | `inScope` + `normalizeName` on `sales_rep` | the only correct entry point — never filter raw rows by hand |
| `isComplete(r)` | completion date **AND** `list === 'Complete'` | **48 rows carry a date but are Holding/Reopened.** A bare `r.complete` test counts them as finished |
| `isWIP(r)` | `start` and not `isComplete` | complete + WIP partition the scoped rows exactly |
| `everCompleted(r)` | completion date, **regardless of current `list`** | first-time completion — for "how many closed out in week X", which must not shrink when a completed survey is later reopened for resurvey. Not a substitute for `isComplete` in WIP/backlog math |
| `normalizeName(n)` | title-cases fully-uppercase reps; keeps roman numerals | SF exports the same rep in mixed casings, splitting their stats |

### The two age metrics — never interchangeable

| metric | definition | used for |
|---|---|---|
| `wipAgeFrom(r)` | **anchor date**: resurvey request → completion +2d → project start | cycle-time math: `ct_total`, `projCt`, `estComplete`. **Never shift it** — Spec 12744 depends on it |
| `ssDaysOpen(r, asOf)` | days the survey has been SS's, = anchor → asOf **minus one rep grace day** | queue triage, the "Days Open in SS" column, attention rules |
| `hasRepGrace(r)` | blank resource counts as rep; straight-to-field skips it; open resurveys get none | `requested` is the rep→field handoff marker (99% coverage on Radicl/SPWR vs 13% on Sales Rep) |
| `isResurveyDefect(r)` | `hasResurveySig` **and** the reason picklist does not say "Unnecessary Request" | What counts against yield. A request raised and then dismissed is not a survey failure — nothing was re-surveyed — so those rows are excluded from the Resurveys page **entirely**, not merely from the percentage. FPY 81.3% → 83.3%. Keep `hasResurveySig` for "did a resurvey happen at all": cohorts, drill segments, the open queue |
| `fpy(completions)` | `(completions − isResurveyDefect) ÷ completions × 100`, or `null` on an empty set | First Pass Yield per Spec 12744. Takes an already-scoped array — the caller owns the population, this owns only the ratio. **Weighted, never a mean of rates**: the 4-week rolling line pools the window's rows in one call, because averaging four weekly percentages lets a 6-completion week pull as hard as a 130-one. Returns `null` rather than 0 on no completions — "no data" is not "perfect yield", and 0 would colour the card red. Lived inline in **eight** places before 2026-08-07 (six in `renderResurvey`, plus `lwFpy`/`pwFpy` on Current); `test/surfaces.test.js` now fails on any inline copy |
| `isOpenResurvey(r)` | resurvey requested, no resurvey-complete date, **and `list !== 'Complete'`** | **18 rows were resolved without the Resurvey Complete Date ever being filled in.** Testing only the dates counts those as still open. Powers the drill-drawer chips, the WIP schedule date, and the Resurveys open queue |
| `inRepGrace(r, asOf)` | still inside the rep's first day | WIP table shows a "Rep day" pill instead of a number |

"Proj Age" (`start → today`) is a *third* number, computed inline on the WIP page.
It is total elapsed age regardless of owner — use it for the age-distribution bar,
never for queue triage.

### SS ratio — two variants, deliberately

| metric | numerator | denominator | answers |
|---|---|---|---|
| `ssRatioForWeek(rows, weekEnd)` | **7-day mean WIP** across the week | 3 most recent complete weeks | "where did week N end" — Trends line, Monday recap |
| `ssRatioLive(rows, asOf)` | WIP right now | 3 weeks ending `lastCompleteWeekEnd()` | "what's on my desk today" — WIP page card |
| `ssRatioBand(v)` | ≤1.0 good · 1–2 uncoloured · ≥2.0 alarm | | shared by both surfaces |

The weekly numerator is a **mean, not a Sunday close**: intake keeps arriving
Fri/Sat while the team is off, so a week-close snapshot samples the weekly
maximum every time and overstates backlog by roughly a third.

Partial weeks are never plotted — the week end is in the future, so WIP counts
every open row while the denominator averages in a barely-started week.

### Flow & alarms

| metric | definition | notes |
|---|---|---|
| `rollingClearance(rows, weekEnd, 4)` | completions ÷ starts over 4 weeks | volume-normalised; the 1-week version is noise (under 100% in 12 of 20 weeks) |
| `weeklyFloor(rows, weekEnd)` | lowest daily WIP across the week (Mon–Sun) | used to assume Monday was always the low point (day after weekend buildup drains); a sustained backlog climb broke that — WIP now often keeps rising all week, so Monday could sit above the real minimum. Fixed 2026-08-07 to take the actual min |
| `clearanceAlarm(series)` | 4-wk clearance <90% twice running | confirmation |

`floorAlarm`/`floorBaseline` (trailing 16-week median × 1.5) were dropped from
the UI 2026-08-07 — the design assumed a stable baseline with occasional
spikes, but against a multi-month sustained climb the trailing median chases
the trend and the alarm flickered true/false with no real change in
trajectory. Functions remain in `lib/metrics.cjs` (tested) pending a redesign
that detects sustained direction instead of a threshold vs. recent history.

The clearance threshold is fit to this team's own 20-week history — it encodes
"unusual for us", not an industry standard. Revisit after a quarter.

### Cycle time & projection

| metric | definition |
|---|---|
| `avg` / `med` / `pct` | ignore null/negative/NaN; `avg` keeps **2dp** |
| `bandFor(v, target)` | ≤target good · ≤target+2 mid · else bad, **on the displayed value** |
| `queueAgeBand(d, targetAvg)` | ≤target good · ≤target+3 mid · else bad. For how long something has been **open**, not how long it took — hence +3 where `bandFor` uses +2. Bands the raw day count, since `ssDaysOpen` returns whole days |
| `buildShowRates(rows, asOf)` | measured per-resource completion-within-1-day rate; ≥5 samples, else global. Retained for reference; the projection no longer calls it |
| `buildExpectedCt(recent)` | rep's own avg (≥3) → region\|resource segment → global |
| `weekDaysRemaining(iso)` | fractional days left Mon–Sun; export day counts as half |
| `buildWeekdayShape(rows, asOf, weeks)` | share of a week's completions landing on each weekday over the trailing window (Sun≈0). Used to spread the projected remainder across remaining days and to derive `remainShare` |
| `buildProjectionModel(allRows, asOf, {rateWeeks 8, levelWeeks 3})` | fits every rate the weekly projection needs from a trailing window. **`allRows` must include cancelled rows** — the conversion drag lives in the denominators. Returns: `pConv(row, asOf, remainShare, schedThisWk)` weekly completion probability for an open row (resource × age-band × booked-or-not hazard table, gentle per-region multiplier, `hazSched≈0.9` for a booked row, `hazRs` for an open resurvey); `walkInPerWeek`/`walkInPerDay`/`walkInMix` (surveys that start **and** finish inside one Mon–Sun week — the "walk-in" a Monday snapshot can't see, ~57% of a rep booking vs ~15% of a Radicl one); `intakePerWeek`/`mix` (trailing booking rate and resource split); `spwrCap` (SunPower-surveyor weekly ceiling ≈ trailing max × 1.15); `cancelNoSurvey` per resource (**diagnostic only** — the drag is already inside `pConv` and the walk-in rate, never multiply it again) |
| `projectWeek(allRows, weekStartISO, asOfISO, {cacheKey, asOfHour, z 1})` | **the weekly completion projection.** `point = completedSoFar + restOfToday + Σ pConv over open WIP + walkInPerWeek × remainShare + SPWR-cap adjustment − recent slippage`. **`restOfToday`** — the export is a moment inside a working day, so a few completions logged by mid-morning does not mean the day is done. Two parts: rows **booked for today** and not yet marked complete (their resource's `hazSched` ≈ 0.9, kept out of `pipeline` so they are not double-counted) + the day's usual **walk-up** beyond that (`today's weekday share × trailing-3wk rate − banked − booked`). Both scaled by `asOfHour` (the export hour, ~0.9 ahead before 9am → ~0.05 after 5pm; surfaces pass `DATA_TS`'s hour; a booked visit keeps a 0.35 floor). `remainShare` covers only the days *strictly after* asOf so nothing here is also in `pipeline` / `intake`. Exposed as `todayScheduled` / `todayScheduledExpected` / `todayWalkExpected`. `remainShare` = fraction of a week's completions still ahead of `asOf` (1.0 Monday-morning, ~0.5 Wed, ~0.1 Fri). **Slippage correction**: a rolling self-backtest at the same day-of-week over `rateWeeks` gives `recentBias` (positive = the model over-projected); `point` subtracts it, clamped to ±30% and only applied with ≥3 backtest weeks — the pipeline hazard is fit on resolved history where a slipped appointment already had its date rewritten, so forward it reads a few completions high. Returns `point`, `lo`/`hi` (± `z`·residual σ, ≥4), `raw`/`adj`, the decomposition (`pipeline`/`pipelineScheduled`/`pipelineUnscheduled`/`intake`/`capAdj`/`slippageAdj`/`byResource`/`byDayIntake`/`byDay`), `recentBias`/`recentMae`/`nBacktest`/`backtest[]`, and `model`. `byDay` is the 7-day view — actual on past days, actual + `restOfToday` on the export day, the leftover spread by the weekday shape on the days after — read by both the breakdown modal's by-day table and the Current "Completions by day" chart's dashed Projected line. The band is `z·min(residual σ, 1.3·MAE)` so one freak week does not blow the range out. `cacheKey` (the surfaces pass `DATA_TS`) memoises the ~150 ms result so a filter change doesn't recompute a number filters never touch. Validated on 10 weeks: Wed read bias +1 / MAE 18, Fri +2 / MAE 5; Monday-morning bias +11 / MAE 29, most of that MAE irreducible (a week's walk-in swings 15–60 and nothing on Monday says which). Surfaced: Current → **Projected total** (hero cell → breakdown modal, with a `_missSpark` track-record sparkline) + the by-day chart's Projected line; compose's daily card, its **Huddle** mode, and its team-card stats; `api/morning-card.js` (`stats.projected`/`projectedLo`/`projectedHi`). compose anchors the call on `DATA_TS`, not `getYesterday()` |
| `trendLabel(cur, prev, band)` | `TREND_BAND_AVG` 0.1 (dashboard) vs `TREND_BAND_MED` 0.3 (compose) — two calculations on purpose |
| Market clustering | `lib/coverage.cjs` `clusterByRadius()` → Map page | **Replaced grouping by town, 2026-08-25.** Town grouping made 833 places out of 2,446 jobs with 470 holding a single job and 73% holding two or fewer — a map of postal names, not of markets, and unable to answer the question the map exists for. A market is every job within a chosen radius of a densest seed, so it is literally "what one surveyor could cover from one base"; its centroid is therefore where a base would sit. Radius is a control (15/25/35mi, default 25) because it is a judgement call, not a constant. Greedy densest-seed, **not** k-means (no k is known — the count is the answer) and **not** DBSCAN (chaining would run Philadelphia into Allentown along a continuous suburb corridor). Deterministic on stable input order, so a market never renames itself between renders. A lat/lon grid picks which pairs to measure — 110ms of all-pairs haversines down to 17ms — and a test asserts the grid returns exactly what all-pairs would |
| Surveyor capacity | `lib/coverage.cjs` `jobsPerDayExact()` / `jobsPerDay()` / `weeklyCapacity()` / `dayBudget()` | A named-minutes budget rather than a lookup: `fieldHoursPerDay·60 − dailyOverheadMinutes − (2 × drive to market) − per job (onSiteMinutes + adminMinutesPerJob + hop)`. Written as a budget so every capacity figure decomposes back into minutes and can be argued with knob by knob. Defaults calibrated to Doug's observed ceiling — 3/day when tight, 2/day at 10–35mi, 1/day past 45 — and every one is overridable per surveyor. **Editable in Settings → Resource model** (2026-08-26): `OpsCoverage.setModel()` rewrites the base every other function reads through `surveyorConfig()`, one assignment point, because callers like `weeklyCapacity(25)` are never handed a cfg at all; a surveyor's own knobs in `roster.json` are merged after and still win. `roadFactor` 1.3 converts straight-line to road miles and is a knob on the config rather than a constant multiplied inside `driveMinutes()`: a stated assumption in one named place, not a measurement. The team total — 4 × 14.8 = **59.2/wk at an 8-mile market** — is spelled out arithmetic-first by `resModelLine()` on the Settings page and in the team drawer, because the page previously printed it with nothing saying where it came from. **`weeklyCapacity` multiplies the EXACT daily rate, not the floored one** — flooring per day then multiplying charged a 2.9 job/day market as 10 a week when it runs ~14.5, understating close-in markets by a third |
| Invoice unit cost | `lib/billing.cjs` `VENDORS` → Billing page | Per-vendor spec, never hardcoded in the rules — a test asserts nothing below the vendor registry names a vendor or its price. Radicl: $20/credit, 14.2 credits ($284) for a survey visit, 9 credits ($180) travel adder beyond ~50mi. **Base, Partial Survey and Go Back all bill at the same 14.2** — a partial and a repeat cost exactly what a completed first survey costs, which is the most important and least visible fact on the invoice |
| All-in cost per survey | `lib/billing.cjs` `summarize()` → Billing rail | Total invoiced ÷ billed survey visits, so travel adders and demobilisation are inside it. Classified `info`, not a dispute — it is not billable-in-error, it is what an incomplete first survey costs, and the invoice is the only place it is recorded |
| Own-defect rework | `lib/billing.cjs` `isOwnDefectRebill()` → Billing | Requires **both** `resurvey_attributed === 'Surveyor'` **and** `resource === vendor.sfResource`. Attribution alone is not enough: a rep-performed survey is also attributed to "Surveyor", meaning the rep. Reading attribution by itself turned 1 real case into an apparent 4 on the first live statement, and a test pins the distinction |
| Duplicate vs repeat visit | `lib/billing.cjs` `reconcile()` → Billing | A first visit followed by a return is a **sequence** (`repeat_visit`, info), not a duplicate — flagging Base→Go Back as a duplicate cried wolf on every legitimate return. `duplicate_charge` fires only on the same account billed the **same charge type** twice. `cross_statement` needs the same account and charge type on two statements under **different dates**: same-date is not flagged and is not stored twice, because overlapping statement periods re-report a charge as a matter of course. Both read 0 on the live history — every apparent duplicate in it was the overlap artefact |
| Charge identity | `lib/statement-import.cjs` `lineIdentity()` / `dedupeHistory()` | What makes two lines the same charge rather than two charges that look alike: vendor + normalised name + normalised address + date + type + subtype + **amount**. Stricter than `accountKey()` on purpose — a false positive here silently deletes money that was really billed. Count-aware: the history keeps as many copies as the statement reporting the most of them, since a statement legitimately repeats a line (up to 3 travel adders for one account on one day). Deduping the two live statements took invoiced spend from **$165,702 to $137,821** — 118 of the 08.24.26 statement's 395 lines were charges 07.01.26–08.08.26 had already billed |
| Cost per account | `lib/billing.cjs` `byAccount()` → Billing → "By account" lens | Sums every charge line an account drew — survey plus any travel adders, cleanup or rework — into one total, keyed on `accountKey()` (last name + street number, stable against name-order and formatting differences between the invoice and Salesforce). Not an average: an account with three travel adders and three surveys reads its true total, not a per-survey figure that hides the count |
| Cost by project outcome | `lib/billing.cjs` `byOutcome()` → Billing → "By outcome" lens | Charge lines grouped by `project_status` on the matched Salesforce survey, with an unmatched bucket so the parts add up to the invoiced total. Only meaningful since the 2026-08-26 report change brought canceled projects into the export — before it, one canceled row was in scope and every dollar looked like it was spent on a live deal. Live: 14% of vendor spend is on projects since canceled, 8% more on At-Risk. `dead` marks Canceled only; At-Risk is a project on its way somewhere, and folding it in would report a number that moves as those projects resolve. | Office mobility | `lib/coverage.cjs` `officeMobility()` → Resource page | Does a sales office's footprint MOVE, or is it merely wide. Half-separation over half-width: split the weeks in two, compare each half's centroid against each half's own radius. Above 1.0 (and 40+ miles) the office was somewhere else by the end. **Two rejected predecessors, both documented in the source**: mean weekly centroid drift measures dispersion, not movement (a wide Oregon territory scored 153mi and never moved, while the PA→VA migration scored 78); straightness fixes that and produces a false negative on the migration itself (0.26, because it worked widely at each end). | Market recommendation | `lib/coverage.cjs` `marketAdvice()` → Resource page | One of Absorb / Deploy / Hire / Coach / Leave with vendor / Gone quiet, from five facts: is the market live, can we reach it, is there enough work, is that work durable, who is doing it badly. `HIRE_WEEKLY` 10 sits near a full week's capacity because a fixed hire must be justified by work that arrives every week; `DEPLOY_WEEKLY` 4 is lower because a posting is reversible. `COACH_MIN_N` 10 completions — at 5, one defect is 20% and would name an office off noise. Called a *recommendation*, not an action (2026-08-26): the page makes a case and the manager decides, and the old name had the table promising more certainty than its thresholds carry |
| Surveyor vehicle cost | `index.html` `resVehicleWeekly()` + `lib/coverage.cjs` `dailyMiles()` → Resource page | Two shapes, decided by `vehicle` in `roster.json`. **`company`** is the flat `vehicleMonthly` ÷ 52 × 12. **`own`** — all four today, and the default for anyone absent from the list — is a mileage reimbursement: 40¢ per road mile, plus 20¢ on every mile past 100 **in a single day**. The bonus is a day rule and is therefore applied per day and multiplied out; applied to a weekly total, a surveyor doing 60 miles five days running would collect a bonus they never earned. Miles are geometry and live in coverage.cjs (round trip + one hop between each pair of jobs, on the exact daily job count, × `roadFactor`); what a mile is worth is payroll and lives with the other cost knobs. **This is the only cost on the page that reacts to the coverage model** — $82/wk at an 8-mile market against $380 at 60, so it is quoted at the same 8-mile market the capacity beside it assumes |

Break-even — surveys a week per surveyor to match the vendor — is the only figure here independent of the capacity model. Currently 4.1/wk against an actual 2.0/wk, i.e. $867/survey, **above** the vendor. Loaded weekly cost is `surveyorAnnual` ÷ 52 plus the vehicle (see the row above), averaged across the roster by `resTeamWeeklyCost()` because two surveyors on different vehicle arrangements cost different amounts. A per-diem and a lodging rate lived in that object feeding nothing and were deleted: a setting that changes no number reads as though somebody already accounted for travel |
| SPWR work per surveyor | `index.html` Resource *The team* | **Attributed to a place, never to a person.** Salesforce records the survey's resource, not which surveyor performed it. Nearest-base attribution was tried and gave Portland entirely to one of two surveyors eight miles apart, printing the other at 0.0 — indistinguishable from idle, and not something the data can say. Work is counted within each surveyor's own day radius instead; overlapping ranges are counted against both and marked *shared range* |


## Invariants the tests enforce

`test/metrics.test.js` — each function against hand-written cases.
`test/snapshot.test.js` — the whole surface against a frozen real-data fixture.
`test/surfaces.test.js` — static guards across surfaces:

1. No surface reimplements the completion test (`!r.complete`)
2. No surface reads a `data.js` const off `window` — they are top-level `const`s,
   so `window.DATA_TS` is always `undefined` and falls through to the wall clock
3. Status bands are never computed inline
4. Shared definitions are imported, not redefined
5. `metrics.cjs` exports everything the surfaces destructure
6. Every `TIP` entry is referenced by a card (a stale tooltip is a lie)

node scripts/build-fixture.cjs      # rebuild the test fixture from data.json

UPDATE_SNAPSHOT=1 npm test          # accept intentional metric changes
